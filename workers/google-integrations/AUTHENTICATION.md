# Firebase ID-token verification and revocation

The Worker verifies Firebase ID tokens locally as RS256 JWTs against Google's published Firebase Secure Token certificates. It validates the project issuer and audience, signature, `exp`, `iat`, `auth_time`, and subject. Certificate downloads are cached according to their cache headers; this is not a Firebase user-session lookup.

Firebase ID tokens normally expire about one hour after issuance. Offline signature verification proves that the token was signed and has not expired, but it does not query Firebase Auth to learn whether an administrator or the user has since revoked that session or disabled the account. The current `auth_time` check only rejects a timestamp in the future; it does not compare against Firebase's revocation time. Therefore, if a token is revoked immediately after issuance, this verifier can accept it until its natural expiration, for a worst-case exposure window of approximately one hour. Although `jwtVerify` is configured with 30 seconds of clock tolerance, the explicit `payload.exp <= now` check rejects an expired token without that extra grace period. A token already near expiry has a shorter remaining window.

Revocation-aware verification requires an online Firebase Authentication lookup, such as the Admin SDK's `verifyIdToken(token, true)` or an equivalent trusted call that checks the user's `tokensValidAfterTime`/disabled state. This adds a network dependency and latency to protected requests and requires server credentials and suitable identity permissions. It is not enabled in this Worker: no paid Firebase dependency or per-request Auth lookup has been added. Firebase's documented Admin SDK flow is described in [Manage User Sessions](https://firebase.google.com/docs/auth/admin/manage-sessions) and [Verify ID Tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens).

An optional future low-cost design would check revocation on sensitive operations or use a short-lived, bounded cache of a successful revocation timestamp lookup. A cache trades immediate revocation detection for its TTL, and outages need an explicit fail-closed/fail-open policy. It should be separately reviewed and approved; this Worker currently performs no such check.
